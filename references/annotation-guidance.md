# Comments, Annotations, and Semantic Views

## Purpose

Comments and annotations translate local business language into metadata that Select AI can place in prompt context. They are not the local dialect itself; they are the mapping from local terms to formal data meaning.

## Recommended placement

| Information | Recommended location |
|---|---|
| Table grain and business purpose | Table comment or description annotation |
| Column meaning and null semantics | Column comment or description annotation |
| Local names, abbreviations, and synonyms | Alias-style annotation |
| Units and currency | Unit-style annotation |
| PK/FK relationships | Database constraints where possible |
| Status-code values that change | Reference table or semantic view |
| Deterministic business calculations | Reviewed view or materialized view |
| Cross-request guidance | `additional_instructions` |
| Long policy or manual content | RAG document corpus |

## Quality checklist

A useful table description states:

- what one row represents
- authoritative source
- refresh cadence or effective-date behavior
- important exclusions
- intended analytical or AI use

A useful column description states:

- business definition
- unit or currency
- null meaning
- allowed values or code-table reference
- sensitivity classification
- which date or amount definition applies

Avoid circular descriptions such as `AMT means amount` or `STATUS is status`.

## Alias example

A business user may ask for `revenue`, `sales`, or a local term. The metadata should map those terms to one reviewed semantic column, such as `AI_SALES_V.REVENUE_AMOUNT`, whose view definition already applies posting, cancellation, and tax rules.

## Verification

Do not assume annotations are used merely because they exist. Enable profile annotation enrichment and inspect `SHOWPROMPT` with a question that should trigger the alias or definition.

## v0.4 collection and advisory reporting

The original sectioned CSV collector remains unchanged. A separate collector is
generated by `scripts/generate_semantics_collector.py`; its JSON is supplied to
the scorer with `--semantics-input`. This isolates optional dictionary features
from legacy collection and preserves multiline values without confusing them
with CSV section markers. The generator never opens a Database connection.

The generated script queries only ordinary tables visible through `ALL_TABLES`,
their non-hidden `ALL_TAB_COLUMNS`, and matching `ALL_ANNOTATIONS_USAGE` rows.
Scope excludes temporary, nested, and secondary tables. It uses validated
unquoted owner names, a restricted LIKE pattern, `SET DEFINE OFF` and SQL binds.
It does not create annotations or domains. Review the resulting SQL before
running it in an authorized, already connected SQLcl session.

### JSON contract

UTF-8 JSON (optionally with BOM), with envelope:

```json
{"format":"oracle-ai-semantics-v1","records":[]}
```

Records use these `type` values:

| Type | Fields |
|---|---|
| `context` | `session_user`, `current_schema`, `target_owner`, `table_like_pattern`, `db_name`, `con_name`, `collected_at`; visibility/scope notes |
| `table` | `owner`, `table_name` |
| `column` | `owner`, `table_name`, `column_name` |
| `annotation` | `owner`, `annotation_owner`, `object_name`, `object_type`, `column_name`, `annotation_name`, `annotation_value`, `domain_owner`, `domain_name`, `origin` |
| `domain` | `owner`, `table_name`, `column_name`, `domain_owner`, `domain_name`, `domain_column_name` |
| `status` | `component` (`scope`, `annotations`, `domains`), `state`, `diagnostic` |

Each component has at most one final status. `scope` covers both table and column
inventory. A missing status means not collected, even if partial records exist.
Only successful components contribute to metrics; a failed component's partial
rows cannot be interpreted as full coverage. Invalid/truncated JSON, duplicate
keys/statuses, and invalid record/state types fail local parsing with a diagnostic.

JSON uses null for absent values. `annotation_value: null` is a legitimate
valueless annotation. The literal string `"NULL"` remains text. Quotes, commas,
Japanese text, control characters and line breaks are escaped as JSON, restored
by the parser, and escaped independently for Markdown/HTML output. Metadata is
never executed as code or instructions. Fields are written on separate JSON
lines to stay below DBMS_OUTPUT's line limit without truncating annotation values.

### Collection states

| State | Meaning |
|---|---|
| `collected` | Complete query succeeded, including zero matching rows |
| `not_collected` | No collection evidence/status for this component |
| `unsupported` | Required column unavailable in a dictionary view confirmed accessible by a separate probe |
| `permission_denied` | Explicit insufficient-privilege error (ORA-01031) |
| `unavailable` | Cause undetermined, including ORA-00942 (missing or invisible view) |
| `error` | Other query/collection error; inspect diagnostic |

Queries for new dictionary columns are dynamic. A capability probe first checks
whether the view itself is accessible; ORA-00904 from the subsequent fixed-column
probe confirms that this collector's required interface is unavailable. It is
not a claim that the whole Database lacks every annotation/domain capability.
No feature is classified from a version number alone.

Zero annotations over a nonempty successfully collected scope means no settings
observed (0.00%). It is distinct from not collected. A zero-column scope is N/A.
Absence from an `ALL_*` view does not prove absence outside this session's visibility.

### Provenance and coverage

The annotation object's owner comes from `ANNOTATION_OWNER`, joined with
`ALL_TABLES.OWNER` and the object name. For TABLE rows, populated `DOMAIN_OWNER`
and `DOMAIN_NAME` identify domain inheritance; both explicitly null identify
direct registration. Incomplete origin metadata or an unrecognized origin stays
UNKNOWN. A column's domain association alone does not establish that every
annotation on it was inherited. View records and domain-definition records are
not treated as table-column evidence. View inheritance, multicolumn/flexible
domain semantics and other advanced inheritance paths are not certified here.

Coverage uses `(owner, table, column)` sets in the intersection of the supplementary
scope and the original assessment. Multiple labels on a column count once;
direct and inherited sets may overlap. All annotated columns, including those
with unknown provenance, count once overall. Domain links are counted
independently, even with no annotations. An incomplete domain identifier is
displayed with `?` for its missing owner or name. Table-only
annotations appear in the inventory and count tables, never columns.

Labels such as DESCRIPTION, ALIASES and VALUES help organize the report; they are
not mandatory. Counts do not establish correct business definitions. A human
must check code mappings, units, exceptions and business rules.

### Independent runtime evidence

The existing profile generator already emits `annotations=true` by default for
NL2SQL and supports SHOWPROMPT smoke tests. No `domains=true` attribute is added.
Metadata registration, stored profile attributes, constructed prompt contents,
generated SQL semantics and execution results require separate evidence.

Use [the manual evidence template](semantics-evidence-template.md) alongside the
report. v0.4 does not parse arbitrary runtime logs or automatically grade/execute
NL2SQL. With no evidence, runtime stages remain unverified. Save SHOWSQL output,
review it, and execute that exact saved SQL. Optional RUNSQL is a separate
generation trial; a numeric or NULL result alone does not identify its hidden SQL.

See [part 3](../examples/bad_ai_ready_part3/README.md) for reproducible local SQL
generation and clearly labeled prior user observations. Three trials per condition
are not a general accuracy guarantee and do not make annotations/domains mandatory.

### Official sources
