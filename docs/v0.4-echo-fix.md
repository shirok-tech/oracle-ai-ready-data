# v0.4 SQLcl ECHO混入の修正報告

> **2026-09-29追記：** 以下の「未実施」は修正時点の記録です。利用者による
> 2026-09-23の実DB再検証では、ECHO ONからの正常収集、SQLCASE警告の除去、
> 不正scan拒否、正常空スコープ、Advisory有無の評価一致、日英HTML目視が確認されました。
> 詳細は[最終検証報告](v0.4-validation-complete.md)を参照してください。

## 修正内容

`oracle_ai_ready_collect.sql`が呼び出し元の`ECHO ON`を引き継ぐと、spoolに
`SQL>`とSQL文が混入する。従来のScorerは、認識できないセクションや列を空の
メタデータとして扱い、0表・0列のまま採点していた。

保存されていた実DB検証ファイルをローカルで読み取り、次の変化を確認した。
Databaseへ再接続した結果ではない。検証ファイルとZIPは変更していない。

| 入力 | 修正前 | 修正後 |
|---|---|---|
| 保存済みECHO混入scan | 0表・0列、総合点0.97、COMMENT gate pass | 先頭のSQL>で入力エラー、CLI終了コード1 |
| 正常な2表・6列の最小fixture | 2表・6列 | 2表・6列、スコア／ゲート不変 |
| 正常run_context＋空inventory | 正常な空スコープとして採点 | 同じ扱いを維持 |

エラーの例：

```text
error: invalid collector input at line 1: SQL> prompt / echoed SQL detected; recollect with SET ECHO OFF before SPOOL
```

### Collector

`scripts/oracle_ai_ready_collect.sql`のSPOOL開始前に`SET ECHO OFF`を追加した。
呼び出し元がECHO ONでも、collectorのCSVを採取する時点ではOFFにする。
収集query、CLI引数、対象範囲、出力ファイル名は変更していない。

### Scorer

採点前の入力検証を追加した。

- CSV値の外にある`SQL>`プロンプト／echo行を拒否する。
- `run_context`、`table_inventory`、`column_inventory`の存在と閉じた境界を確認する。
- `run_context`は`TARGET_OWNER`と`PROFILE`（scan／rag）を持つ有効な1行を要求する。
- inventoryの必須header・識別値、CSV列数、重複header／section、表と列の対応を検証する。
- 引用された複数行CSVの中にある`SQL>`、セクション記号、空行、引用符は値として保持する。
  引用されていないフィールドの裸の引用符でecho検出を回避する入力は拒否する。
- 不正入力ではstderrにエラーを出し、終了コード1で停止する。レポートや改善SQLは
  出力せず、既存の出力先ファイルも変更しない。

正常な空スコープは、run_contextが有効で、2つのinventoryセクションが明示的に存在する
場合に受け付ける。headerのみ、空区間、`no rows selected`のいずれも扱う。
バージョン行・全体footerを持たない既存の最小形式も維持する。
空スコープのスコア／ゲート条件は変えていないため、その結果を実データの適格性の
証拠と解釈しない。今回の変更は入力検証であり、採点式の変更ではない。

### セマンティクスCollectorのSQLCASE警告

`scripts/oracle_ai_semantics_collect.sql.in`から`SET SQLCASE MIXED`を削除した。
この設定を除き、辞書query、入力bind、由来判定、収集状態、JSON構築は変更していない。

ローカルのSQLcl Release 25.4で、DB未接続の`/nolog`セッションによるクライアント設定だけを
確認した。`SET SQLCASE MIXED`と`SET SQLCASE UPPER`は`is Obsolete.`、`SHOW SQLCASE`は
`SP2-0158`となった。このクライアントで有効なcase変換設定として扱われない観測と、
Collectorがcase変換を必要としない構造が、削除の根拠である。

[Oracle SQLcl 25.4のSET一覧](https://docs.oracle.com/en/database/oracle/sql-developer-command-line/25.4/sqcug/set-system_variable-value.html)
にはSQLCASEがまだ掲載されているため、「公式文書から削除済み」とは扱わない。
実DBでの収集結果の同一性は、以下の再検証で確認する必要がある。

## 実DBでの再検証手順

以下は利用者が検証用Databaseで実施する手順であり、今回未実施。
既存scanとログを保存したまま、新しいディレクトリを使う。旧CollectorのSPOOLは
同名ファイルをreplaceするため、元の証跡ディレクトリでは実行しない。

### 1. ECHO ONから2表・6列を収集

リポジトリのルートから新しい作業ディレクトリを作る。

```bash
mkdir validation_echo_fix_r01
cd validation_echo_fix_r01
sql /nolog
```

SQLclで検証Userへ接続する。`adb_high`は実環境の接続識別子に置き換え、パスワードは
対話入力する。既に接続済みならCONNECTは不要。

```sql
CONNECT BAD_AI_READY@adb_high
SET ECHO ON
@../scripts/oracle_ai_ready_collect.sql BAD_AI_READY AIRD\_T0_ scan
SHOW ECHO
```

収集開始前にECHOがOFFとなり、scan内にプロンプトとSQL文が混入しないことを確認する。
既存ラボにAIRD_T02とAIRD_T03がある前提で、run_contextとinventoryを確認する。
他の同パターン表がある環境では、実際の対象範囲に合わせる。

OS側での補助確認：

```bash
grep -nE '^[[:space:]]*SQL>' oracle_ai_ready_scan_BAD_AI_READY_scan.out
python3 ../scripts/score_oracle_ai_ready_scan.py \
  oracle_ai_ready_scan_BAD_AI_READY_scan.out \
  --output lab_echo_fix.md --html-output lab_echo_fix.html
```

期待値はgrepの一致なし、Scorer終了コード0、2表・6列。grepだけでCSVの完全性を
保証せず、Scorerの検証結果と実inventoryを確認する。

### 2. 正常な空スコープ

別の新しいディレクトリで、実際に一致する表がないパターンを指定して収集する。
例：`NO_MATCH_ECHO_FIX_%`。run_contextと両inventory区間が存在し、Scorerが終了コード0で
0表・0列を認識することを確認する。必須区間の欠落やSQLエラーを空スコープと扱わない。

### 3. セマンティクスCollectorを再生成

リポジトリのルートで、新しい出力先へ生成する。

```bash
python3 scripts/generate_semantics_collector.py \
  --owner BAD_AI_READY --table-like 'AIRD\_T0_' \
  --output validation_echo_fix_r01/collect_semantics.sql \
  --spool-file semantics_echo_fix_r01.json
```

検証ディレクトリで起動したSQLclから`@collect_semantics.sql`を実行する。
SQLCASEのObsolete警告が出ないこと、JSONの収集状態・件数・値・由来が前回の正常な
証跡と一致することを確認する。collected_atなど日時の違いは区別する。
SPOOL CREATEは既存ファイルを置き換えないので、再試行には新規ファイル名を使う。

### 4. Advisory有無の比較と異常入力の拒否

同じ正常scanを使い、`--semantics-input semantics_echo_fix_r01.json`の有無だけを変えて
レポートを生成する。スコアとCOMMENTゲートが同じで、意味情報だけが追加されることを
確認する。今回の最小ラボなら、2／6列、coverage 33.33%、direct 1、inherited 1、
domain-linked 1が目安になる。

保存した混入scanは、別の出力先でScorerへ渡し、終了コード1・stderrエラー・新規出力なしを
確認する。混入scanを手で加工して正常な収集結果と見なさない。

残す証跡は、SQLclバージョン、ECHO ONからの実行記録、正常／空のscan、Collector JSON、
Advisory有無のレポート、異常入力のstderrと終了コード。接続パスワード・APIキー・トークンは
含めない。再検証にDDL/DML、Profile再作成、外部LLM呼び出しは不要。
