## 主な設計判断

既存CollectorのCSVとCLIを維持し、任意のJSON補助Collectorを採用した。
新辞書の可視性・列差異で旧収集を壊さず、改行・引用符・カンマ・日本語・値なし
Annotationを安全に保持するためである。ローカルPythonは読み取り専用SQLを生成する
だけで接続しない。入力検証、bind変数、動的な辞書probe、JSON escapingを使用する。

scopeは現セッションに見える普通の表とその列。レポートの母数は元の評価対象との
共通部分とし、取得していない列を0%扱いしない。ANNOTATION_OWNERを対象表のownerと
照合し、Domain由来は辞書のDOMAIN_OWNER／DOMAIN_NAMEを根拠にする。矛盾・不足は
不明のまま残す。値の正しさやランタイム成功は件数から推定しない。

SQLclの出力設定とautocommitを明示し、未完了transactionへcommit／rollbackを発行
しない。証跡の上書きを避けるSPOOL CREATEを使用する。端末エラーと収集日時の確認は
必要であり、詳しくは[利用手順](USAGE.md#optional-annotationdomain-assessment-v040)を参照。

1. [利用手順](USAGE.md#optional-annotationdomain-assessment-v040)で対象schema・table範囲の
   補助SQLをローカル生成し、レビュー後に検証用SQLclセッションで実行する。
2. 新規ファイル名のJSONと端末エラーを確認し、session_user・対象範囲・collected_at・
   component状態・診断情報を保存する。元のscan出力と合わせてScorerへ渡す。
3. 必要なら[第3回手順](../examples/bad_ai_ready_part3/README.md)に従い、実行User所有の
   既存Credential名と明示したモデルで最小比較を行う。
4. 辞書→Profile属性→SHOWPROMPT→SHOWSQL保存→レビュー→保存SQLそのものの実行を記録。
   RUNSQLは必要な場合だけ別試行として保存する。
5. [証跡テンプレート](../references/semantics-evidence-template.md)と、元scan・補助JSON・
   Databaseバージョン・Profile属性・試行番号・SHOWPROMPT・保存SQL・レビュー・実行結果を
   提出する。パスワード、APIキー、トークンは含めない。
